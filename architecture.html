§1

What this is

One Go binary, one SQLite file. A request comes in over HTTP, the binary handles it end to end, and the only thing it talks to on disk is greenlight.db. No Postgres, no Docker, no separate database process to keep alive.

§2

The three layers

Every request flows top to bottom through exactly three layers. Nothing skips a layer — the model layer never imports net/http, and handlers never write raw SQL.

Why it matters — business rules are unit-testable without a server, and the transport (HTTP today) could change without touching a single query.
§3

Directory map

One file per resource in the HTTP layer, one package per concern underneath. Two conventions decide where anything lives: cmd/ vs. internal/ is standard Go project layout, and the packages inside internal/ mirror the three layers from §2.

cmd/api/
The HTTP server — everything transport-specific
main.go
wires config, logger, db, models, mailer
routes.go
URL → handler table, and the middleware chain
middleware.go
8 middlewares — auth, rate limiting, CORS, panic recovery…
*.go
one file per resource: healthcheck, movies, users, tokens
helpers.go / errors.go
shared JSON helpers · every error response shape
cmd/seed/
CLI that creates a demo user + sample movies
internal/
Go-enforced private code — nothing outside the module can import it
data/
model layer — domain types (Movie, User, Token…) and their SQL
db/
storage layer — opens the SQLite connection pool, runs migrations
envflag/
lets every flag fall back to a GREENLIGHT_* environment variable
mailer/
SMTP client + embedded email templates
validator/
generic "collect field errors into a map" helper
assert/
tiny generic assertion helpers used by every test
testutil/
fresh migrated test database per test; doc.go guides the whole suite
migrations/
Versioned .sql schema files, embedded into the binary

Why cmd/ and internal/: this split isn't project-specific — it's standard Go project layout. cmd/ holds main packages, one subdirectory per binary (cmd/api the server, cmd/seed the demo-data command). internal/ is special to the toolchain itself: a package rooted under an internal/ directory can only be imported by code rooted at that directory's parent — the compiler enforces it, not a convention people can ignore. That's why data, db, envflag, mailer, validator, and testutil all live there: none of them are meant to be imported from outside this module.

Why data/ and db/ are split: keeping the model layer and storage layer as separate packages is what makes it physically impossible for internal/data to accidentally depend on net/http, and what lets internal/db be swapped or exercised in isolation (via internal/testutil) without touching a single query. envflag, mailer, validator, and testutil don't fit either layer — they're cross-cutting support code — but still need the same compiler-enforced privacy, so they sit beside data/db rather than in their own top-level directory.

§7

Process lifecycle

Three phases, spread across two files: cmd/api/main.go holds main and run, cmd/api/server.go holds serve. Startup is a straight line; shutdown is the part with an order that matters.

7.1

Startup

main() does as little as possible — call run(), print whatever error comes back, exit. run() returns that error instead of calling os.Exit, because os.Exit skips deferred calls and this function has one that matters.

7.2

Serving

serve() builds the http.Server — the routes as its handler, a timeout on every axis, and the app's slog handler wired to ErrorLog so the server's own errors come out as JSON too. Four kinds of goroutine then coexist. Note that app.routes() isn't purely a wiring call: building the middleware chain is what starts the rate limiter's janitor.

7.3

Shutdown — the ordering is the design

A signal arrives and the two goroutines converge on a single buffered channel. Read the two columns as independent timelines that meet where the arrows cross.

Why this order — srv.Shutdown goes first so requests drain before anything they might use is dismantled. app.stop() second, once nothing is being served, because killing the janitor mid-request would pull the rug from under a live handler. app.wg.Wait() last, because that work has no other exit condition. Reversing the last two would mean waiting forever on an endless loop, or signalling a half-sent email to stop — see §8.

Three sharp edges. The 30s grace bounds srv.Shutdown only — the wg.Wait() after it is unbounded. A second Ctrl+C does nothing, because registering with signal.Notify removed Go's default terminate-on-signal behaviour; aborting a wedged drain takes SIGKILL. And any error from ListenAndServe other than ErrServerClosed — a port already in use, say — returns immediately, leaving the signal goroutine parked on <-quit forever. Harmless on the way out, but it makes serve() a once-per-process call.

§8

Load-bearing decisions

Four choices worth knowing before you change something that depends on them.

Dependency injection via a struct

Every handler is a method on *application — no globals. That's what lets each test build a fully isolated app.

Sentinel errors only

The model layer returns ErrRecordNotFound / ErrEditConflict upward; handlers translate those to status codes. SQL never leaks past internal/data.

A fresh SQLite file per test

Every test gets its own file in t.TempDir(), migrated fresh. No mocking, no shared fixtures, safe in parallel.

Background work gets its own recovery

recoverPanic only guards the request's goroutine — a panic in a spawned one kills the process otherwise, so app.background() wraps every background task in its own recover.

Two mechanisms for background goroutines

app.wg means wait for this to finish — per-request work like a welcome email, which graceful shutdown blocks on. app.shutdown means tell this loop to stop — a channel closed by app.stop() that long-lived loops select on. Waiting on an endless loop would hang; telling a half-sent email to stop would lose it.

§9

How it's tested

One external test dependency (github.com/google/go-cmp); everything else is the standard library. The full guide — commands, conventions, and the Go testing machinery involved — lives in internal/testutil/doc.go, readable with go doc greenlight/internal/testutil.

mise run test
go test -race ./... — the everyday command
mise run test/short
skips database-backed tests
mise run test/cover
coverage with -coverpkg=./..., opens an HTML report
mise run test/fuzz
30s of fuzzing per package
mise run test/bench
benchmarks with allocation counts
mise run audit
tidy + fmt + vet + test -race

Layers of the suite, outside-in. Nothing is mocked except outbound email, and there are no database mocks anywhere — SQLite is embedded, so a real database is a temp file costing about a millisecond. Since the thing most likely to be wrong in a model layer is the SQL, and a mock cannot check SQL, that is a far better trade than it would be against Postgres.

End-to-end HTTP

cmd/api/*_test.go — a real httptest.Server, real database, real middleware chain. Includes the full access-control matrix and serve() under a genuine SIGTERM, proving in-flight requests and background email both finish before shutdown returns.

Model layer

internal/data/*_test.go — the SQL itself, against the real migrated schema. Optimistic locking, foreign-key cascades, the sort safelist, token scoping.

Concurrency

concurrency_test.go — 20 goroutines writing at once (guarding busy_timeout), readers running during writes (guarding WAL), and two racing updates where exactly one must win and no write may be lost. All under -race.

Connection setup

internal/db/db_test.go — checks out four connections simultaneously and asserts every PRAGMA on all of them. That's what defeats the "run PRAGMA foreign_keys = ON once at startup" mistake, which a single-connection test would happily pass.

Email

internal/mailer — template rendering, HTML escaping and MIME structure, asserted on the bytes sent to a fake in-process SMTP server written in the test file. No SMTP dependency.

Fuzzing

Four targets on the hand-written parsers: Runtime.UnmarshalJSON, Genres.Scan, readJSON, EmailRX. They assert properties — never panics, accepted input round-trips unchanged, and an accepted email address can never contain a line break (SMTP header injection).

Measuring coverage — mise run test/cover passes -coverpkg=./.... Without it go test -cover instruments only the package under test, and internal/db reads 0% despite being exercised by nearly every test in the repo through internal/testutil. Current: validator 100%, envflag 100%, mailer 93%, data 91%, cmd/api 86%, db 85%, cmd/seed 73% — 87% module-wide, the remainder mostly main/run process wiring.
